RISK 01: BROWSER REDIRECT CACHING DESTROYING CLICK TRACKING
--------------------------------------------------------------------------------
- Category: HTTP Routing & Browser Behavior
- Severity: CRITICAL | Probability: HIGH
- Root Cause:
  If the redirect endpoint returns an HTTP 301 (Moved Permanently) or an HTTP 308
  (Permanent Redirect), modern browsers (Chrome, Firefox, Safari) store the target
  URL in their persistent disk cache. On subsequent visits by the same user or machine,
  the browser navigates directly to the destination without contacting the Next.js
  server at all. Consequently, the tracking route is bypassed and clicks are lost.
- Impact:
  Repeat visits will fail to increment click counts or log timestamps, directly
  violating the requirement: "Every time someone visits a short URL, it should be tracked".
- Concrete Engineering Solution:
  1. Never return HTTP 301 or 308 for short links.
  2. Use HTTP 307 (Temporary Redirect) or HTTP 302 (Found).
  3. Explicitly set cache-busting headers to prevent intermediate proxies and browsers
     from caching the redirect response.
  Implementation Snippet (`app/[code]/route.ts`):
  ```typescript
  return new NextResponse(null, {
    status: 307,
    headers: {
      Location: originalUrl,
      'Cache-Control': 'no-store, no-cache, must-revalidate, proxy-revalidate',
      'Pragma': 'no-cache',
      'Expires': '0',
    },
  });
  ```

RISK 02: RESERVED ROUTE COLLISIONS ON DYNAMIC ROOT PATH `/[code]`
--------------------------------------------------------------------------------
- Category: Next.js App Router Architecture
- Severity: HIGH | Probability: HIGH
- Root Cause:
  In Next.js App Router, placing a dynamic route at `app/[code]/route.ts` intercepts
  all single-segment root paths. If a short code matches an application route or
  static asset request (e.g., `/api`, `/_next`, `/favicon.ico`, `/robots.txt`, `/analytics`),
  Next.js will attempt to resolve it as a short URL instead of executing the internal route.
- Impact:
  - Generating short code "api" breaks all REST API calls.
  - Browser requesting `/favicon.ico` triggers a database lookup, logs a false click,
    or throws a 404.
  - Next.js internal chunk loading (`/_next/...`) can be intercepted.
- Concrete Engineering Solution:
  1. Implement a strict Reserved Keywords Guard at both code generation time and routing time.
  2. Reserve list: `['api', '_next', 'favicon.ico', 'robots.txt', 'sitemap.xml', 'analytics', 'dashboard', 'static']`.
  3. Implementation Snippet:
  ```typescript
  const RESERVED_SLUGS = new Set([
    'api', '_next', 'favicon.ico', 'robots.txt', 'sitemap.xml', 'analytics', 'dashboard'
  ]);

  export function isReservedSlug(slug: string): boolean {
    return RESERVED_SLUGS.has(slug.toLowerCase()) || slug.startsWith('_');
  }
  ```
  At generation time: If generated code matches `isReservedSlug`, retry generation.
  At redirect time: If `isReservedSlug(code)` is true, return `NextResponse.next()` or 404.

RISK 03: SQLITE DATABASE LOCKING (`SQLITE_BUSY`) & DEV HOT-RELOAD LEAKS
--------------------------------------------------------------------------------
- Category: Database & Concurrency
- Severity: HIGH | Probability: MEDIUM
- Root Cause:
  1. Standard SQLite uses a traditional rollback journal where write operations lock
     the entire database file against concurrent reads and writes.
  2. In Next.js development mode, Fast Refresh reloads modules on every save, creating
     multiple SQLite database connection instances. These stale connections hold file
     descriptors, leading to `SqliteError: database is locked`.
- Impact:
  Concurrent click recording or URL creations crash with HTTP 500 `SQLITE_BUSY`.
- Concrete Engineering Solution:
  1. WAL Mode: Immediately upon opening SQLite, enable Write-Ahead Logging (WAL) and set a busy timeout:
     ```sql
     PRAGMA journal_mode = WAL;
     PRAGMA synchronous = NORMAL;
     PRAGMA busy_timeout = 5000;
     ```
     WAL allows multiple readers to read concurrently while a write transaction proceeds.
  2. Global Connection Singleton: Prevent hot-reload connection leaks by attaching the instance
     to `globalThis` in development:
     ```typescript
     import Database from 'better-sqlite3';

     declare global {
       var _sqliteDb: Database.Database | undefined;
     }

     export function getDb(): Database.Database {
       if (!globalThis._sqliteDb) {
         globalThis._sqliteDb = new Database('data/shortener.db', { timeout: 5000 });
         globalThis._sqliteDb.pragma('journal_mode = WAL');
         globalThis._sqliteDb.pragma('synchronous = NORMAL');
       }
       return globalThis._sqliteDb;
     }
     ```

RISK 04: INFINITE REDIRECT LOOPS (SELF-REFERENCING URLS)
--------------------------------------------------------------------------------
- Category: Application Security & Availability
- Severity: HIGH | Probability: MEDIUM
- Root Cause:
  A user pastes a short URL generated by this application (e.g., `http://localhost:3000/xyz`)
  or the app's root URL as the destination URL to be shortened. Visiting the resulting short URL
  triggers a recursive redirect chain (`A -> B -> A` or `A -> A`).
- Impact:
  The browser detects `ERR_TOO_MANY_REDIRECTS`, exhausts client memory, and floods the server
  with hundreds of synthetic click entries within seconds.
- Concrete Engineering Solution:
  1. Parse the long URL using `new URL(rawUrl)`.
  2. Inspect the hostname and protocol. Reject any URL whose hostname matches `localhost`,
     `127.0.0.1`, `0.0.0.0`, or the deployed host environment variable (`process.env.APP_HOST`).
  3. Implementation Snippet:
  ```typescript
  export function validateDestinationUrl(urlStr: string, currentHost: string): { valid: boolean; error?: string } {
    try {
      const parsed = new URL(urlStr);
      if (!['http:', 'https:'].includes(parsed.protocol)) {
        return { valid: false, error: 'Only http and https protocols are allowed.' };
      }
      if (parsed.host === currentHost || parsed.hostname === 'localhost' || parsed.hostname === '127.0.0.1') {
        return { valid: false, error: 'Cannot shorten links pointing back to this service.' };
      }
      return { valid: true };
    } catch {
      return { valid: false, error: 'Malformed URL format.' };
    }
  }
  ```

RISK 05: MALICIOUS PROTOCOLS (XSS, SSRF, ARBITRARY SCHEMES)
--------------------------------------------------------------------------------
- Category: Web Security
- Severity: HIGH | Probability: MEDIUM
- Root Cause:
  Without strict protocol validation, attackers can submit URI schemes such as:
  - `javascript:alert(document.cookie)` -> Cross-Site Scripting (XSS) when clicked.
  - `data:text/html,...` -> Phishing / page spoofing.
  - `file:///etc/passwd` -> Local file disclosure attempts.
- Impact:
  Severe security vulnerability; compromising users who click shortened links.
- Concrete Engineering Solution:
  1. Enforce strict protocol whitelist: ONLY `http:` and `https:`.
  2. If the user omits the protocol (e.g. `example.com`), prepend `https://` before validation.
  3. Validate maximum URL length (max 2048 characters) to avoid database memory exhaustion.

RISK 06: SHORT CODE COLLISIONS & RACE CONDITIONS
--------------------------------------------------------------------------------
- Category: Data Integrity
- Severity: MEDIUM | Probability: MEDIUM
- Root Cause:
  Pseudo-random generators will eventually produce identical codes as the URL database
  grows (Birthday Paradox). If concurrent requests attempt to insert the same code,
  unhandled database unique constraint errors occur.
- Impact:
  Uncaught `SQLITE_CONSTRAINT_UNIQUE` exception leads to HTTP 500 error for users.
- Concrete Engineering Solution:
  1. Use Base62 characters `[0-9a-zA-Z]` with length 6 (62^6 = ~56.8 billion possibilities).
  2. Wrap database insertion in an automatic retry loop (up to 3 attempts with fresh code generation).
  3. Implementation Snippet:
  ```typescript
  export function createShortUrl(originalUrl: string): UrlRecord {
    const db = getDb();
    const maxAttempts = 3;
    for (let attempt = 0; attempt < maxAttempts; attempt++) {
      const code = generateNanoCode(6);
      if (isReservedSlug(code)) continue;
      try {
        const stmt = db.prepare(
          'INSERT INTO urls (id, code, original_url, created_at) VALUES (?, ?, ?, ?)'
        );
        const id = nanoid();
        const now = new Date().toISOString();
        stmt.run(id, code, originalUrl, now);
        return { id, code, originalUrl, createdAt: now };
      } catch (err: any) {
        if (err.code === 'SQLITE_CONSTRAINT_UNIQUE') continue; // Collision: retry
        throw err;
      }
    }
    throw new Error('Failed to generate unique short code. Please try again.');
  }
  ```

RISK 07: FRONTEND HYDRATION MISMATCHES & CLIPBOARD API FAILURES
--------------------------------------------------------------------------------
- Category: Frontend & User Interface
- Severity: MEDIUM | Probability: MEDIUM
- Root Cause:
  1. Next.js Server Components cannot access browser APIs (`window`, `navigator.clipboard`).
     Referencing them in SSR triggers `ReferenceError: navigator is not defined`.
  2. `navigator.clipboard.writeText()` is restricted to Secure Contexts (HTTPS). In plain HTTP
     or unsupported browsers, it rejects or throws a security error.
- Impact:
  Clipboard copy fails silently or crashes the user interface.
- Concrete Engineering Solution:
  1. Mark form and list components with `'use client'`.
  2. Implement an asynchronous copy utility with a reliable fallback:
  ```typescript
  export async function copyToClipboard(text: string): Promise<boolean> {
    if (typeof window === 'undefined') return false;
    if (navigator?.clipboard?.writeText) {
      try {
        await navigator.clipboard.writeText(text);
        return true;
      } catch (e) {
        // Fallback on permission denial
      }
    }
    // Fallback for non-secure contexts or legacy browsers
    try {
      const textArea = document.createElement('textarea');
      textArea.value = text;
      textArea.style.position = 'fixed';
      textArea.style.left = '-9999px';
      document.body.appendChild(textArea);
      textArea.focus();
      textArea.select();
      const successful = document.execCommand('copy');
      document.body.removeChild(textArea);
      return successful;
    } catch {
      return false;
    }
  }
  ```

RISK 08: UNINDEXED DATABASE QUERIES & TABLE SCAN LATENCY
--------------------------------------------------------------------------------
- Category: Database Performance
- Severity: MEDIUM | Probability: HIGH
- Root Cause:
  - Redirect route queries `WHERE code = ?` on every visit.
  - Analytics dashboard queries `COUNT(*)` and timestamp logs `WHERE url_id = ? ORDER BY timestamp DESC`.
  - Without explicit database indices, SQLite executes a full table scan on every click.
- Impact:
  Redirect latency climbs from < 1ms to hundreds of milliseconds as traffic increases.
- Concrete Engineering Solution:
  1. Create indices directly during database schema initialization:
  ```sql
  CREATE UNIQUE INDEX IF NOT EXISTS idx_urls_code ON urls(code);
  CREATE INDEX IF NOT EXISTS idx_clicks_url_time ON clicks(url_id, timestamp DESC);
  ```
  2. In `app/[code]/route.ts`, use prepared statements (`db.prepare(...)`) which are parsed
     and cached by SQLite, ensuring O(1) indexed lookup times.

RISK 09: BOT / PREFETCH TRAFFIC INFLATING ANALYTICS METRICS
--------------------------------------------------------------------------------
- Category: Analytics Accuracy
- Severity: LOW | Probability: HIGH
- Root Cause:
  1. When a user pastes a short link into Slack, Discord, Twitter, or iMessage, the platform's
     bot immediately issues a GET request to fetch preview metadata (`og:title`, etc.).
  2. Modern browsers (Chrome Speculation Rules, `<link rel="prefetch">`) prefetch links on hover.
- Impact:
  Click counts are inflated by automated bots before any human user clicks the link.
- Concrete Engineering Solution:
  1. Inspect request headers:
     - Detect `purpose: prefetch` or `sec-purpose: prefetch` and ignore or flag as prefetch.
     - Inspect User-Agent for known crawler signatures (`Slackbot`, `Twitterbot`, `Discordbot`,
       `facebookexternalhit`, `curl`, `Postman`).
  2. Flag or categorize records: Add an `is_bot` boolean or record the detected client type
     so analytics can separate human clicks from automated previews.

--------------------------------------------------------------------------------
RISK 10: TIMEZONE INCONSISTENCIES & LARGE CLICK LOG DOM FREEZING
--------------------------------------------------------------------------------
- Category: Data Representation & Rendering
- Severity: LOW | Probability: MEDIUM
- Root Cause:
  1. Storing local server timestamps causes timezone confusion when viewed by clients in different regions.
  2. If a URL receives thousands of clicks, rendering thousands of `<tr>` elements simultaneously
     causes severe browser DOM re-layout lag.
- Impact:
  Inaccurate time reporting and UI freeze when opening analytics for high-volume URLs.
- Concrete Engineering Solution:
  1. Store all timestamps in ISO 8601 UTC format (`YYYY-MM-DDTHH:mm:ss.sssZ`).
  2. Render client-side using `Intl.DateTimeFormat` or browser local time, displaying both
     formatted local date/time and relative time ("X minutes ago").
  3. Paginate or slice the detailed clicks table to the top 100 most recent records,
     while showing total aggregates across all records.
